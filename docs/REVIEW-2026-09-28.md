### S1 · WhatsApp: a process would start for every free user who opens the app  [critical · High mode]
- **Status: DONE 28 Sep 2026 (not deployed yet).** manager.mjs rewritten (linked-or-link-page spawn rule, idle-stop, free cap
  `WA_MAX_FREE_WORKERS`=10, heap 512 MB + RSS guard 700 MB, crash backoff + 10-min park with auto-retry, port pool,
  staggered linked-only restore, wait for the old process before a plan-change restart, `/manager-status` worker list);
  index.mjs (box-wide whisper lock, no transcription without AI, unhandledRejection logger); wa proxy forwards `?link=1`;
  WhatsApp page polls `/api/wa/status?link=1`. Tested with a fake Baileys harness. Not done from the list: item 6 `-t 1`
  (kept 2 threads now that one runs at a time), notify.ts sender (now answered 409 without a process).
- `src/lib/journey.ts:31` calls `/api/wa/status` for every signed-in user on every screen change (Finish-setup bar).
- The pending change makes `/api/wa/[...path]/route.ts` send a far-future expiry for free users, and
  `bridge/manager.mjs:141-150` starts a worker (`startWorker`, one `node` process each, ~70–150 MB) for ANY request with a
  future expiry — even for numbers never linked. Workers are respawned on exit (`:86-90`), restored at every boot
  (`:160-166`), never idle-stopped; unlinked workers keep reconnecting and cycling QR codes forever (index.mjs close handler).
- On a 3.6 GB box already running cPanel, Postgres, Next, the partner app and video rendering, ~20 such processes = out of
  memory → the Linux OOM killer stops random processes → site, partner panel and bots go down. Many unauthenticated
  WhatsApp connections from one IP may also hurt the paying numbers.
- Also: `src/lib/notify.ts:128-136` sends through the user's own id when `NOTIFY_WA_USER` is unset (spawns workers for
  unlinked users); voice-note transcription (`index.mjs:346,1527`) runs per worker with a per-process lock and also for free
  (no-AI) numbers (~390 MB each whisper run).
- Fix:
  1. manager: start a worker only if `tenants/<id>/auth/creds.json` shows a linked account, OR the request is a linking
     action from the WhatsApp page (`/qr`, `/pair`, `/status?link=1`). Otherwise answer `{state:"disconnected", linked:false}`
     without spawning. The WhatsApp page's LinkBox passes `?link=1`; journey/connect pages don't.
  2. Idle-stop: a worker not connected and not polled by the link page for 10 min exits; meta marks it unlinked so boot does
     not restore it.
  3. `MAX_WORKERS` (15 while on 3.6 GB) → friendly "WhatsApp service busy, try in a while" + owner alert.
  4. Spawn workers with `--max-old-space-size=192`; manager restarts a worker above ~300 MB RSS (read /proc/<pid>/status).
  5. Restore at boot one per second; per-tenant crash backoff (2.5 s → 5 min, park after 5 crashes in 10 min); port pool
     8800–8999 released on exit (today `nextPort++` never reuses).
  6. Skip transcription when `!aiActive()`; box-wide lock (`flock -n /tmp/wa-whisper.lock`), `-t 1`, cap notes at 60 s.
- Done when: a free user who never linked opens every app screen and `ps -eo rss,args | grep bridge/index.mjs` shows no new
  process; linking still works; paid bots unchanged.

## C · Bots and background jobs

### C1 · WhatsApp bot hardening  [High]
- One DB error wipes the card data for up to 5 min (`index.mjs:552-558`, `cardContext = null`) → leads not saved, CRM log
  missing, bot answers without card facts. Keep the last good value; retry every 30 s; queue lead/CRM writes.
- No timeouts on Gemini (`index.mjs:98-102`) and most fetches; add 25 s / 10 s. Add `unhandledRejection` handler.
- State files written in place (`index.mjs:399,412,461,469,670,693`, `manager.mjs:38`); unreadable → silent defaults (bot
  re-enabled, never-reply list emptied). Use temp-file + rename + .bak; SIGTERM handler that saves creds; pm2 kill_timeout.
- Disconnect codes: 401 → clear + mark unlinked + stop; 403/411/500 → stop + alert; 440 → stop.
- Manager proxy timeout 20 s vs callers 60–120 s (Status posts reported failed but actually sent → owner retries → double
  post) → longer timeout for /status and media sends, 504 "may still complete", idempotency key.

### C2 · Every-minute jobs  [Medium]
- pm2 `cron_restart` kills a still-running job each minute (`ecosystem.config.cjs:16-17`); `wa-broadcast.mjs` sends 80 items

  items "sending" first; same for crm-webhooks and social-autoreply. crm-webhooks: fetch only due rows (next_attempt_at) and
  cap per owner so one broken endpoint can't block everyone for a day.

### C3 · Video jobs  [Medium]

  boot. Add refund_due + retry loop, checked final write, 10-min sweep. `scripts/cleanup-30d.mjs:64` marks recently edited
  long videos as removed and deletes their saved scenes → go by actual deleted files / updated_at.

### C4 · pm2 setup  [Medium]
- App runs through `/usr/bin/npm` with no memory limit (`ecosystem.config.cjs:7`); WhatsApp manager no limit; no restart
